Welcome & Auth (§4.13) — sign-in block · component drafts A/B/C

Three distinct directions to de-clunk the landing's sign-in block — the owner flagged the wall of three stacked full-width buttons (SIGN IN / CREATE ACCOUNT / Sign in with Apple) and the heavy full-width black Apple bar. Each draft kills the three-equal-buttons stack and lightens Apple, spanning conservative → bold. Shown on iOS (Apple present); the Android fork drops Apple (AUTH-03). Everything stays on the §1.5 catalog — flat Scanline keycaps (F-03), square on-screen chrome (F-07), F-06 type (21/15/11/9), no on-screen gold/pink (F-02/F-05), the orange StateMark for selection (F-09). The rest of the landing (the games hero above + the locked NavBand below) is unchanged. Stage 1 shows the sign-in block (the bit flagged as clunky); Stage 2 shows how each draft handles the OTHER half — the Create Account form (AUTH-01 · the AUTH-10 age-13/ToS gate · MOD-07 live username availability), in that draft's own idiom.

A — quiet the secondaries

One full-width button, not three. SIGN IN stays the lone orange primary; CREATE ACCOUNT drops to a text link in a "New to InGame?" footer; Apple shrinks to a compact, content-hugging button under an "OR CONTINUE WITH" rule — no longer a black slab. FORGOT? moves inline on the password label row, tightening the rhythm.

Same single-form model as today — pure presentation, zero behavior change. Nothing ripples to product-spec / api-contract. Lowest risk; the safe pick if the goal is just "less heavy."

B — segmented mode toggle

Returning vs new is one decision, made once, at the top. CREATE ACCOUNT is a tab, not a button — the stack is gone. Apple rides compact below as "OR USE."

Flow note: this folds the W2 create-account step onto the landing (today it's its own screen). That's a flow change — I'd confirm it against the product-spec AUTH flow + log an OQ before it converges. Strongest hierarchy of the three.

C — email-first / progressive

The lightest front door: one field, one button. EMAIL + CONTINUE only; the password (or the create-account beat) reveals on the next step once we know the email. Apple sits compact under an OR. The button-wall is impossible here — there's only ever one primary on screen.

Behavior note: this changes the AUTH model — one CONTINUE + an email-probe to branch sign-in vs create. The biggest product-spec / api-contract ripple of the three (a new "does this email exist" step). Worth an OQ + a second artboard for step 2 if you want to pursue it.
