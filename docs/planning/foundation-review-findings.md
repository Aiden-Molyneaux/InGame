### F-01 · HIGH · Part 2 — Nothing enforces that code actually *uses* the single seams (defineRoute / @mutation); every seam-keyed invariant can be bypassed by simply not adopting the seam
- **Where:** `tools/lint/rules/rule-04-authz.mjs:20-30` (inventory parsed from `defineRoute` literals only) · `tools/lint/rules/rule-05-events.mjs:12` (scans only `mutation({...})` blocks) · `CONVENTIONS.md:76` (F43: the `@mutation` marker "is the single seam the authz-test, outbox-emit, and audit-row checks all key off") · `docs/planning/m2-entry-plan.md` §5 G-E ("the single ACH-08 emit seam is the only mutation path (un-bypassable)").
- **Problem:** rule-04 and rule-05 verify properties *of seam users*, never *seam adoption*. A route registered with plain Express (`router.post(...)`) produces no `defineRoute` literal → no inventory entry → no SYS-07 authz-test requirement, and it also dodges rule-03's schema-from-shared check (which only runs in files containing `defineRoute`). Likewise a service method that calls a repository write *without* the `mutation({...})` wrapper escapes rule-05, the outbox emission, AND the transactional MOD-10 audit row — the three checks F43 says "can't be escaped" all key off a marker whose presence is voluntary. No rule flags raw `router.*`/`app.*` registration or a repo-write call outside a `mutation()` context.
- **Why it matters:** SYS-07 (the "prototype's original-sin guard"), ACH-08 (no-retrofit events), and MOD-10 (no un-auditable history) are the project's four load-bearing invariants, and M2 is being built by an external agent whose discipline these lints exist to backstop. G-E's "un-bypassable" claim is currently a convention, not a mechanism — the exact gap class this review was asked to find. Only the owner gates and the F29 clone-pattern instruction stand between a forgotten wrapper and a silent, unaudited, untested mutation path.
- **Suggested resolution:** two small additive lints: (a) **route-registration guard** — any `app.<verb>(`/`router.<verb>(` call outside the one sanctioned bootstrap file fails CI ("register via defineRoute"); (b) **seam-adoption guard** — a repository write-method invocation (`.update(`/`.delete(`/`.insert(` on a repo import) inside `services/` that is not lexically inside a `mutation(` block fails CI (same windowed-heuristic style as rule-02). Add one bad-PR corpus fixture per guard. Alternatively (stronger, type-level): make repos' write methods require a `MutationCtx` parameter only `mutation()` can construct.
- **Status:** NEW

### F-02 · HIGH · Part 2 — rule-02 scope-lint examines only three Drizzle call shapes; relational reads, raw SQL inside repositories, and inserts fall entirely outside it
- **Where:** `tools/lint/rules/rule-02-scoping.mjs:11` (`ACCESS_RE = /\.(from|update|delete)\(\s*(ident)/`).
- **Problem:** the SYS-01 scope-lint's remit is "every read/modify of user-owned data goes through the scoped helper" (CONVENTIONS rule 2), but the regex only sees `.from(table)`, `.update(table)`, `.delete(table)`. Escapes: **(a)** Drizzle's relational API — `db.query.collectionEntries.findMany(...)` is a first-class read path with no `.from(` and is never examined; **(b)** raw SQL — `db.execute(sql\`SELECT … FROM collection_entries WHERE id = ${id}\`)` inside a repository: rule-01 skips repository files, and rule-02's regex extracts no table identifier, so raw SQL in repos has **zero** scoping oversight; **(c)** inserts are declared out of remit ("you cannot IDOR a brand-new actor-stamped row") — but nothing verifies the stamp: an insert taking `userId` from request data (a friendship row, an adoption row for someone else) is a cross-user write no rule sees. Also: the `SYS-01-EXEMPT` branch at line 70-71 is dead code (global tables are `continue`d at line 64 before the exemption is consulted), so the documented exemption mechanism does nothing.
- **Why it matters:** this is the IDOR domain the project calls its original sin. A repo written with the relational API — idiomatic Drizzle, likely for an agent — silently exempts itself from the fail-closed allowlist. The lint's fail-closed posture is real only for the three matched shapes.
- **Suggested resolution:** extend detection to (a) `db.query.<ident>.` (map ident → table via `toSnake`), (b) any `execute(`/`sql\`` occurrence in a repository file → require a scope-signal in the window or fail ("raw SQL needs the scoped helper or a listed-global table in an EXEMPT"), (c) either add `.insert(` with an actor-stamp heuristic or write the "inserts are safe" premise into a standing SYS-07 insert-with-foreign-owner test obligation. Delete or fix the dead EXEMPT branch. Add corpus fixtures for each new shape. File this as the OQ the M2 brief refers to (note: **no OQ-118 exists in `docs/open-questions.md`** — the newest is OQ-117 — so this gap is currently unlogged anywhere).
- **Status:** NEW (contrary to the task brief, it is *not* already filed)

### F-03 · MED · Part 2 — rule-03 guards `req.body` only: query/params are never validated, the presence check is file-level, and the shared-schema requirement applies only inside defineRoute files
- **Where:** `tools/lint/rules/rule-03-zod.mjs:8,29-40,43` · CONVENTIONS rule 3 ("**Every input** is zod-validated").
- **Problem:** three coverage holes vs the stated remit: **(a)** `req.query` / `req.params` are not inspected at all — yet the contract is full of query-driven inputs (`?q=`, `sort`, `order`, `cursor`, `?u=`, `?targetType=`), which are exactly the unbounded-string / enum-injection inputs SYS-02's policy covers (a voluntary `usernameAvailabilityQuerySchema` exists in shared, proving the need); **(b)** the check is per-file, not per-use — one `.parse(` anywhere silences every other raw `req.body` read in the same file; **(c)** the "schema must be imported from `@ingame/shared`" check runs only in files containing `defineRoute`, so a controller hand-rolling `z.object({...}).parse(req.body)` locally passes both checks, violating "never hand-rolled."
- **Why it matters:** M3's collection/search endpoints are almost entirely query-param-shaped; as written, none of that input surface is mechanically forced through shared schemas, and SYS-02's "all write requests validated" quietly narrows to "bodies, in the files we happen to scan."
- **Suggested resolution:** add `req.query`/`req.params` to the raw-input regex (same validate-nearby requirement, or a `validateQuery(...)` chokepoint); make the check window-scoped per occurrence like rule-02; run the shared-import check on every `validateBody|validateQuery` call site regardless of `defineRoute` presence. Corpus fixtures for each.
- **Status:** NEW

### F-04 · MED · Part 2 — rule-04's coverage credit is a file-level conjunction, and the `mutates` flag has no backstop for mislabeled routes
- **Where:** `tools/lint/rules/rule-04-authz.mjs:46-49` (`coveredByActorB4xx`) · `:54` (`needsAuthz = mutates || crossPrincipal`).
- **Problem:** a route counts as covered when one test **file** contains the authzTest token *somewhere*, any 4xx assertion *somewhere*, and the string "actorB" *somewhere* — three independent file-level tests, not one test that does all three. One broad integration file (many routes, one legit actor-B 4xx test) satisfies every token it merely mentions; the rule's own promise ("a name-match satisfied by expect(200) does NOT count") only holds against files with *no* 4xx anywhere. Separately, `mutates` is hand-declared: a POST/PATCH/DELETE route with `mutates` omitted (or `false`) requires no authz test, and no method-based cross-check exists (the flag was designed to catch state-changing GETs, but nothing catches a non-flagged non-GET).
- **Why it matters:** the inventory-diff is G-D's counting mechanism ("authz-test count == mutating-endpoint count"); both holes let the count lie in the safe-looking direction as the endpoint surface grows M3+.
- **Suggested resolution:** scope the three predicates to a single test block (e.g. locate the token, then apply the 4xx + actor-B regexes within the enclosing `it(...)`/`test(...)` span via `matchBalanced`); add a backstop: `method !== 'get' && !mutates` fails CI unless the route carries an explicit `readonly: true`-style justification. Corpus fixtures: a token-in-comment file with an unrelated 4xx; a POST with `mutates` omitted.
- **Status:** NEW

### F-05 · MED · Part 1 — AUTH-11's anti-enumeration claim ("the throttled availability check is the only existence signal") is contradicted by the register endpoint's duplicate-email disclosure
- **Where:** `docs/spec/product-spec.md:108` (AUTH-11: "…so the throttled availability check is the **only** existence signal") vs `docs/spec/api-contract.md:39` (`POST /auth/register` → "**`VALIDATION_ERROR`** with field-targeted detail: **duplicate email**/username…").

Option (a) is a wording fix, not a behavior change.
